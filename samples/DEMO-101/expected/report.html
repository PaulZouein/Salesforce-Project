Root cause

CaseEscalationService.applyPremiumPriority stops processing the whole batch at the first case whose account is not Premium: line 30 is return; inside the loop over the batch, where the comment above it ("nothing to do" for this case) describes a continue (E5). Every Premium case that comes after such a case in the same insert keeps the priority it arrived with.

Evidence chain:

  1. Symptom in data. The only Premium cases that are not High are three imported cases, and each one follows a Standard-account case in its import batch (E1, E2).
  2. Code that produces it. The trigger hands the whole batch to the service (E3, E4), and the service returns from the method at the first non-Premium case (E5).
  3. Observed in the failing transaction. In the 11 November import, the first case belongs to a Standard account (E9), statement 30 executes, the method exits and statement 32 never runs (E10). The Premium case inserted in the same batch, 500Ws00000C0006IAA, is Medium (E1, E11).
  4. Why only sometimes. A case created by hand is a batch of one, so the early return has nothing left to skip. An imported batch is affected only when a non-Premium case precedes a Premium one: the 12 November batch contains only Premium cases and is correct (E1).
  5. Why re-saving does not help. The update path re-applies the rule only when the account changes (E6).
  6. Why the notification is missing. The flow notifies only when Priority is High (E7). It evaluated to false for both cases of the 11 November batch because the trigger had left them at Medium (E12). The missing notification is a consequence of this defect, not a second defect. The flow does not write Priority (E7) and did not change in November (E15).

One point is not established by an artifact and is labelled accordingly. Hypothesis: the position of each case inside the 10 November batch is taken from case-number order (E1); there is no debug log for that run. The 11 November batch, for which the log exists, does not depend on this.

The full diff, including the new test method mixedBatchEscalatesEveryPremiumCase in CaseEscalationServiceTest, is in fix.diff.

Why this layer. The rule already lives in CaseEscalationService, and the defect is one statement in it. Correcting that statement keeps a single place that decides the priority. Moving the rule into the flow, or adding a second automation, would leave two places to maintain and would not remove the faulty loop.

Impact. The method has two callers, both in CaseTriggerHandler (E4, E16); the test class is the only other component that references the service (E16). For a batch of one, and for a batch whose cases are all Premium or all non-Premium, behaviour is unchanged. For a mixed batch, Premium cases after a non-Premium case now become High, on insert and on an account change. The flow needs no change: once the priority is High before save, its decision is true and it notifies (E7).
